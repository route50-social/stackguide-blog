AWS Lightsail에 Next.js·PostgreSQL 서비스 배포하기: 서버 만들기부터 HTTPS까지

AWS를 처음 쓰는 사람을 기준으로, Next.js와 PostgreSQL로 만든 서비스를 Lightsail 서버 한 대(Ubuntu 24.04)에 올리는 과정을 인스턴스 생성, 고정 IP·방화벽, Node.js·PostgreSQL 설치, systemd·Nginx 설정, 도메인과 HTTPS, 재배포와 백업 순서로 정리합니다.

로컬에서는 npm run dev로 잘 돌아가는 Next.js 서비스가 있고, 데이터는 PostgreSQL에 저장합니다. 이제 이걸 인터넷에 올려 다른 사람도 쓰게 하고 싶은데, AWS 콘솔을 열어 보니 메뉴가 너무 많습니다. 이 글은 그중 가장 단순한 길인 Amazon Lightsail 서버 한 대에 Next.js와 PostgreSQL을 함께 올리는 방법을 처음부터 끝까지 따라갈 수 있게 정리했습니다.

용어 풀이

  • Lightsail(Amazon Lightsail): AWS가 서버, 디스크, 공인 IP, 일정량의 데이터 전송량을 묶어 월 고정 요금으로 파는 간편형 가상 서버 서비스입니다.
  • Next.js: React로 화면을 만들고, 같은 프로젝트 안에서 서버 코드(API, 서버 렌더링)까지 함께 돌릴 수 있는 웹 프레임워크입니다.
  • PostgreSQL: 표 형태로 데이터를 저장하고 SQL로 다루는 오픈 소스 관계형 데이터베이스입니다.
  • SQL(Structured Query Language, 구조화 질의 언어): 데이터베이스에 데이터를 넣고, 찾고, 고치는 데 쓰는 표준 언어입니다.

다 끝나면 이런 모습이 됩니다. 방문자가 https://내도메인으로 들어오면 Lightsail 방화벽을 지나 서버 안의 Nginx가 요청을 받고, Nginx는 같은 서버에서 도는 Next.js에 요청을 넘깁니다. Next.js는 같은 서버의 PostgreSQL에서 데이터를 읽어 응답합니다. 외부에 열리는 문은 웹(80·443번)과 관리용 SSH(22번)뿐이고, Next.js(3000번)와 PostgreSQL(5432번)은 서버 안에서만 접근할 수 있게 둡니다.

그림 1. 이 글에서 만드는 배포 구조 (자료: Next.js 셀프 호스팅 문서·Lightsail 방화벽 문서, 2026-11-12 확인)

용어 풀이

  • Nginx: 웹 요청을 받아 정적 파일을 내주거나 뒤쪽 프로그램에 요청을 전달하는 웹 서버 프로그램입니다.
  • 리버스 프록시: 방문자의 요청을 대신 받아 뒤에 있는 애플리케이션 서버로 넘겨 주는 중간 서버입니다. Next.js 공식 문서는 직접 운영할 때 Next.js 서버를 인터넷에 바로 노출하지 말고 Nginx 같은 리버스 프록시를 앞에 두라고 권합니다.
  • 포트: 한 서버 안에서 여러 프로그램이 각자 연결을 받도록 나눈 번호입니다. 웹은 보통 80(HTTP)·443(HTTPS), SSH는 22번을 씁니다.
  • HTTPS: 웹 통신을 TLS로 암호화한 방식입니다. 브라우저 주소창의 자물쇠 표시가 이것을 뜻합니다.
  • SSH(Secure Shell): 원격 서버에 암호화된 연결로 접속해 명령을 실행하는 방법입니다. 리눅스 서버를 관리할 때 기본으로 씁니다.
  • 방화벽: 서버로 들어오는 연결 가운데 허용한 포트·주소만 통과시키는 장치입니다. Lightsail 방화벽은 허용 규칙만 만들 수 있고, 규칙에 없는 연결은 모두 막힙니다.
  • DNS(Domain Name System): example.com 같은 도메인 이름을 서버의 IP 주소로 바꿔 주는 인터넷의 주소록입니다.

이 글의 기준

  • 서버: Lightsail, 서울 리전, Ubuntu 24.04 LTS 블루프린트, 월 $12 플랜(메모리 2GB, vCPU 2개, SSD 60GB, 전송량 3TB)
  • 소프트웨어: Node.js 24.22.3(NodeSource 저장소), Next.js 16.4.6, PostgreSQL 16.15, Nginx 1.24.0(둘 다 Ubuntu 24.04 기본 패키지)
  • 확인 방법: 서버 안에서 실행하는 명령은 Windows 11의 Docker 컨테이너(ubuntu:24.04 이미지, 메모리 2GB·CPU 2개로 제한)에서 2026-11-12에 직접 실행해 확인했습니다. 새로 만든 Next.js 프로젝트에 PostgreSQL을 조회하는 API를 하나 넣고, 빌드부터 Nginx를 거친 응답까지 확인했습니다.
  • 확인하지 못한 부분: Lightsail 콘솔 화면 조작과 실제 인스턴스에서의 동작, 도메인 연결, HTTPS 인증서 발급은 AWS 공식 문서와 Certbot 공식 안내로만 확인했습니다. 그래서 콘솔 화면 캡처 대신 메뉴 이름을 공식 문서의 영문 표기 그대로 적었습니다. 컨테이너에는 systemd가 돌지 않아 서비스 파일은 systemd-analyze verify로 문법만 검사했습니다.

용어 풀이

  • 리전: AWS 데이터센터가 모여 있는 지역 단위입니다. 서울 리전(ap-northeast-2)을 고르면 국내 방문자에게 응답이 빠릅니다.
  • 블루프린트: Lightsail 인스턴스를 만들 때 고르는 이미지입니다. 운영체제만 있는 것(OS Only)과 WordPress 같은 앱이 미리 깔린 것(Apps + OS)이 있습니다.
  • vCPU(virtual CPU, 가상 CPU): 가상 서버에 배정되는 CPU 단위입니다. Lightsail의 작은 플랜은 평소에는 정해진 기준 성능만큼만 쓰다가 잠깐씩 더 높은 성능을 내는 방식입니다.
  • Ubuntu: 서버에 많이 쓰는 리눅스 배포판입니다. 24.04는 2024년 4월에 나온 버전입니다.
  • LTS(Long Term Support, 장기 지원): 보안 수정을 오랫동안 받을 수 있도록 지정한 버전입니다. Ubuntu와 Node.js 모두 운영 서버에는 LTS 버전을 권합니다.
  • Node.js: 브라우저 밖에서 JavaScript를 실행하는 런타임입니다. Next.js 서버가 이 위에서 돕니다.
  • 패키지 저장소: apt 같은 패키지 관리자가 프로그램을 내려받는 곳입니다. NodeSource는 Node.js 새 버전을 Ubuntu용 패키지로 제공하는 외부 저장소입니다.
  • API(Application Programming Interface): 프로그램끼리 데이터를 주고받도록 정해 둔 창구입니다. 이 글에서는 Next.js 안에 만든, 데이터베이스 조회 결과를 돌려주는 주소를 말합니다.
  • Docker·컨테이너: 컨테이너는 프로그램과 실행 환경을 묶어 다른 프로그램과 격리해 돌리는 방식이고, Docker는 이를 만들고 실행하는 도구입니다. 여기서는 Ubuntu 서버를 흉내 낸 시험 환경으로 썼습니다.
  • systemd: Ubuntu를 비롯한 대부분의 리눅스에서 프로그램(서비스)의 시작·중지·자동 재시작을 맡는 관리자입니다. systemctl 명령으로 다룹니다.

시작 전에: 준비물과 비용

준비할 것은 세 가지입니다.

  1. AWS 계정: 결제 수단(카드)을 등록해야 합니다.
  2. 코드 저장소: GitHub 같은 곳에 올려 둔 Next.js 프로젝트. package-lock.json이 함께 커밋되어 있어야 서버에서 로컬과 같은 버전의 패키지를 설치할 수 있습니다.
  3. 도메인(선택): HTTPS를 쓰려면 필요합니다. 도메인 없이도 IP 주소로 접속해 확인하는 단계까지는 진행할 수 있습니다.

비용은 서버 한 대 값이 대부분입니다. Lightsail은 시간 단위로 요금을 매기되 월 플랜 가격을 넘지 않으며, 인스턴스를 중지해도 삭제할 때까지 요금이 계속 붙습니다. 아래 금액은 2026년 11월 12일 Lightsail 요금 페이지 기준(세금 별도, 미국 달러)입니다.

용어 풀이

  • 인스턴스: AWS에서 빌려 쓰는 가상 서버 한 대를 부르는 말입니다.
  • 플랜(번들): Lightsail에서 서버 사양, 디스크, 전송량을 하나로 묶은 요금 단위입니다.
  • 공인 IP·고정 IP(Static IP): 공인 IP는 인터넷에서 서버를 찾아올 수 있게 하는 공개 주소이고, 고정 IP는 서버를 껐다 켜도 바뀌지 않도록 계정에 잡아 두는 공인 IP입니다.
  • 스냅샷: 특정 시점의 디스크 내용을 통째로 저장한 백업본입니다. 이 스냅샷으로 같은 상태의 새 서버를 만들 수 있습니다.
  • 관리형 데이터베이스: 설치, 보안 업데이트, 백업을 클라우드 사업자가 대신 맡아 주는 데이터베이스 서비스입니다.

$12 플랜을 기준으로 잡은 이유는 메모리입니다. 이 구성에서는 Next.js 서버, PostgreSQL, Nginx가 한 서버의 메모리를 나눠 쓰고, 코드를 고칠 때마다 서버에서 next build도 돌립니다. 시험 컨테이너에서 새로 만든 Next.js 프로젝트는 메모리 2GB 제한 안에서 약 4초 만에 빌드되었고, 빌드 프로세스 한 개의 최대 메모리는 약 420MB였습니다. 다만 이것은 페이지 몇 개짜리 시작 프로젝트의 값이라, 페이지와 패키지가 많은 실제 서비스는 더 많이 씁니다. 1GB 플랜으로 시작한다면 빌드가 메모리 부족으로 멈출 수 있다는 점을 염두에 두세요.

신규 계정이라면 AWS 프리 티어 크레딧(최대 $200)을 Lightsail에도 쓸 수 있습니다. 예전에 있던 Lightsail 전용 3개월 무료 체험은 새 고객에게 더 이상 제공되지 않는다고 Lightsail FAQ에 적혀 있습니다. 크레딧 조건과 Lightsail·EC2 중 어느 쪽이 맞는지는 Amazon Lightsail vs EC2 저사양 인스턴스에서 따로 비교했습니다.

용어 풀이

  • 프리 티어(Free Tier): AWS가 신규 고객에게 일정량을 무료로 주는 제도입니다. 2025년 7월 15일 이후 가입한 계정은 기간 한정 크레딧 방식입니다.

작업 순서 한눈에 보기

전체 과정은 Lightsail 콘솔에서 하는 일 세 가지와, 서버에 접속해 하는 일 여섯 가지로 나뉩니다. 순서를 바꾸면 막히는 곳이 있어서(예: 443번 포트를 열기 전에 인증서를 받으려 하면 실패) 번호 순서대로 진행하는 것이 좋습니다.

그림 2. 배포 작업 순서. 13은 Lightsail 콘솔, 49는 서버 터미널에서 합니다.

1. Lightsail 인스턴스 만들기

Lightsail 콘솔에 로그인하면 일반 AWS 콘솔과 다른, 훨씬 단순한 화면이 나옵니다. 메뉴는 영문 기준으로 적습니다.

  1. 홈 화면에서 Create instance를 누릅니다.
  2. 인스턴스 위치(리전과 가용 영역)가 서울이 아니면 Change AWS Region and Availability Zone을 눌러 서울(ap-northeast-2)로 바꿉니다. 가용 영역은 기본값을 둬도 됩니다.
  3. 운영체제 종류는 Linux/Unix로 두고, 이미지는 OS Only 쪽에서 Ubuntu 24.04 LTS를 고릅니다.
  4. 네트워크 유형은 듀얼 스택(IPv4와 IPv6)을 고릅니다. IPv6 전용 플랜은 더 싸지만 고정 IP를 붙일 수 없고, IPv6로 접속하지 못하는 방문자가 아직 있습니다.
  5. 플랜은 월 $12(메모리 2GB)를 고릅니다.
  6. 인스턴스 이름을 입력합니다(예: myapp-prod). 영문·숫자·마침표·하이픈·밑줄로 2~255자입니다.
  7. Create instance를 누르면 몇 분 안에 인스턴스가 실행 상태(Running)가 됩니다.

용어 풀이

  • 가용 영역: 한 리전 안에서 전원·네트워크가 분리된 데이터센터 묶음입니다.
  • IPv6·듀얼 스택: IPv6는 주소가 모자란 IPv4를 대신하려고 만든 새 인터넷 주소 체계이고, 듀얼 스택은 두 주소를 함께 쓰는 방식입니다.

Apps + OS 탭에 Node.js 블루프린트도 있지만 여기서는 쓰지 않았습니다. Lightsail 문서에 따르면 이 블루프린트는 Node.js와 함께 MariaDB(MySQL 계열)가 들어 있어, PostgreSQL을 쓰는 프로젝트에는 결국 필요 없는 것을 걷어내야 합니다. 운영체제만 있는 상태에서 필요한 것만 설치하는 편이 구성을 이해하기도 쉽습니다.

2. 고정 IP 붙이기

처음 받은 공인 IP는 인스턴스를 중지했다가 다시 켜면 바뀝니다. 도메인을 연결할 서버라면 이 단계를 건너뛰면 안 됩니다.

  1. 왼쪽 메뉴에서 Networking을 누르고 Create static IP를 고릅니다.
  2. 리전이 인스턴스와 같은지(서울) 확인하고, 붙일 인스턴스로 방금 만든 것을 고릅니다.
  3. 이름을 정하고 Create를 누릅니다.

인스턴스 관리 화면의 Networking 탭에서 공인 IP 옆에 파란 핀 표시가 보이면 고정 IP가 붙은 것입니다. 이 주소를 메모해 두세요. 고정 IP는 인스턴스에 붙어 있는 동안 무료지만, 인스턴스를 지운 뒤 고정 IP만 남겨 두면 1시간 뒤부터 요금이 붙으니 함께 정리해야 합니다.

3. 방화벽에 HTTPS 열고 SSH 좁히기

Ubuntu 블루프린트의 기본 방화벽 규칙은 SSH(22번)와 HTTP(80번)를 모든 IP에 열어 둔 상태입니다. HTTPS(443번)는 기본으로 열려 있지 않아서 직접 추가해야 합니다.

  1. 인스턴스 이름을 눌러 관리 화면으로 들어가 Networking 탭을 엽니다.
  2. IPv4 Firewall 영역에서 Add rule을 누르고, Application에서 HTTPS를 고른 뒤 Create를 누릅니다.
  3. 아래쪽 IPv6 Firewall 영역에서도 똑같이 HTTPS 규칙을 추가합니다. Lightsail은 IPv4와 IPv6 방화벽을 따로 관리하므로 한쪽만 열면 다른 쪽 방문자는 접속하지 못합니다.

3000번(Next.js)과 5432번(PostgreSQL)은 열지 않습니다. 둘 다 같은 서버 안에서만 통신하면 되기 때문입니다.

SSH는 모든 IP에 열려 있으면 전 세계에서 비밀번호·키 대입 시도가 들어옵니다. 집이나 사무실처럼 접속하는 곳의 IP가 정해져 있다면 SSH 규칙의 연필(Edit) 아이콘을 눌러 Restrict to IP address를 고르고 내 IP를 적으세요. 이때 Allow Lightsail browser SSH/RDP를 함께 체크해야 콘솔의 브라우저 SSH가 계속 동작합니다. 체크하지 않으면 브라우저 SSH도 막힙니다. 집 인터넷처럼 IP가 가끔 바뀌는 환경이라면, 바뀐 뒤에는 콘솔에서 규칙의 IP를 고치면 됩니다.

4. 서버에 접속해 필요한 프로그램 설치하기

접속하기

가장 쉬운 방법은 브라우저 SSH입니다. 인스턴스 관리 화면의 Connect 탭에서 Connect using SSH를 누르면 새 창에 터미널이 열리고, ubuntu 사용자로 로그인된 상태가 됩니다. 별도 프로그램도, 키 파일도 필요 없습니다.

내 컴퓨터의 터미널에서 접속하고 싶다면 오른쪽 위 계정 메뉴의 Account → SSH keys 탭에서 서울 리전의 기본 키(.pem 파일)를 내려받습니다. macOS·리눅스에서는 다음처럼 접속합니다.

# 내 컴퓨터(macOS·리눅스)에서 실행. 키 파일 경로와 IP는 자신의 값으로 바꿉니다.
chmod 400 ~/Keys/LightsailDefaultKey-ap-northeast-2.pem
ssh -i ~/Keys/LightsailDefaultKey-ap-northeast-2.pem ubuntu@<고정 IP>

Lightsail이 개인 키를 보관해 주는 것은 리전별 기본 키뿐입니다. 직접 만든 키를 등록했다면 그 개인 키를 잃어버리는 순간 내 컴퓨터에서는 접속할 수 없게 됩니다(브라우저 SSH는 계속 쓸 수 있습니다). 이 키 파일은 비밀번호와 같으니 저장소나 메신저에 올리지 마세요.

설치하기

아래부터는 모두 서버 터미널에서 실행합니다. 먼저 패키지 목록을 갱신하고 보안 업데이트를 적용한 뒤 Git, Nginx, PostgreSQL을 설치합니다.

# 서버에서 실행 (Ubuntu 24.04, ubuntu 사용자)
sudo apt update && sudo apt upgrade -y
sudo apt install -y git nginx postgresql

업그레이드 도중 설정 파일을 바꿀지 묻는 화면이 나오면 기본값(현재 설정 유지)을 고르면 됩니다. 커널이 업데이트되었다면 sudo reboot로 한 번 재부팅하고 다시 접속하세요.

Node.js는 Ubuntu 기본 저장소의 버전이 오래되었으므로 NodeSource 저장소에서 설치합니다. 2026년 11월 기준 Node.js의 LTS 계열은 22, 24, 26이며, 이 글은 24를 썼습니다. Next.js 16.4.6은 Node.js 20.9.0 이상을 요구합니다(next 패키지의 engines 값).

# 서버에서 실행: NodeSource 설치 스크립트를 내려받아 내용을 확인한 뒤 실행
curl -fsSL https://deb.nodesource.com/setup_24.x -o nodesource_setup.sh
less nodesource_setup.sh   # 내용을 훑어본 뒤 q로 나옵니다
sudo bash nodesource_setup.sh
sudo apt install -y nodejs
node -v

시험 환경에서는 node -v가 v24.22.3, npm -v가 11.19.1을 출력했습니다. 인터넷에서 받은 스크립트를 관리자 권한으로 실행하는 것이라 파일로 받아 내용을 먼저 보는 순서로 적었습니다.

5. PostgreSQL에 데이터베이스와 사용자 만들기

Ubuntu의 PostgreSQL 패키지는 설치하자마자 서비스가 실행되고, 기본 설정이 localhost에서만 연결을 받습니다(/etc/postgresql/16/main/postgresql.conf의 listen_addresses 기본값). 같은 서버의 Next.js만 접속하면 되므로 이 설정은 바꾸지 않습니다.

용어 풀이

  • localhost(127.0.0.1): 컴퓨터가 자기 자신을 가리키는 주소입니다. 이 주소로만 연결을 받는 프로그램은 같은 서버 안에서만 접속할 수 있습니다.

앱이 쓸 사용자와 데이터베이스를 만듭니다. 비밀번호는 URL에 그대로 넣어도 문제없도록 16진수 문자열로 만드는 것이 편합니다.

# 서버에서 실행: 비밀번호로 쓸 무작위 문자열 생성 (출력값을 안전한 곳에 기록)
openssl rand -hex 24

# PostgreSQL 관리자(postgres)로 접속
sudo -u postgres psql

psql 프롬프트(postgres=#)가 나오면 다음을 입력합니다. <DB_PASSWORD>는 위에서 만든 값으로 바꿉니다.

CREATE ROLE appuser WITH LOGIN PASSWORD '<DB_PASSWORD>';
CREATE DATABASE appdb OWNER appuser;
\q

접속이 되는지 확인합니다.

# 서버에서 실행
psql "postgresql://appuser:<DB_PASSWORD>@localhost:5432/appdb" -c "select version();"

PostgreSQL 16.15 ... on x86_64-pc-linux-gnu처럼 버전이 나오면 성공입니다(시험 컨테이너의 실제 출력 기준). 로컬에서 쓰던 데이터를 옮겨야 한다면 로컬에서 pg_dump -Fc로 덤프 파일을 만들어 scp로 서버에 올린 뒤 pg_restore -d appdb <파일>로 복원합니다.

용어 풀이

  • psql: PostgreSQL에 접속해 SQL 명령을 입력하는 기본 터미널 도구입니다.
  • pg_dump·pg_restore: PostgreSQL에 포함된 백업·복원 도구입니다. -Fc는 압축된 사용자 지정 형식으로 저장하라는 옵션이고, 이 형식은 pg_restore로 되돌립니다.
  • scp: SSH 연결을 이용해 컴퓨터 사이에 파일을 복사하는 명령입니다.

6. 코드를 내려받고 빌드하기

저장소 접근: 배포 키

비공개 GitHub 저장소를 서버에서 내려받으려면 인증이 필요합니다. 내 계정의 비밀번호나 개인 토큰을 서버에 두는 대신, 그 저장소 하나만 읽을 수 있는 배포 키를 쓰는 것이 안전합니다. 서버가 털리더라도 다른 저장소나 계정 권한까지는 넘어가지 않습니다.

# 서버에서 실행: 배포 키 생성 (Enter를 눌러 기본값 사용)
ssh-keygen -t ed25519 -C "lightsail-deploy" -f ~/.ssh/github_deploy -N ""
cat ~/.ssh/github_deploy.pub

출력된 공개 키(ssh-ed25519 ...로 시작하는 한 줄)를 복사해 GitHub 저장소의 Settings → Deploy keys → Add deploy key에 붙여 넣습니다. Allow write access는 체크하지 않습니다. 그다음 서버가 GitHub에 접속할 때 이 키를 쓰도록 설정하고 저장소를 내려받습니다.

# 서버에서 실행: GitHub 접속에 배포 키를 쓰도록 설정
cat >> ~/.ssh/config <<'EOF'
Host github.com
  IdentityFile ~/.ssh/github_deploy
  IdentitiesOnly yes
EOF
chmod 600 ~/.ssh/config

# 저장소 내려받기 (<OWNER>/<REPO>는 자신의 저장소로 바꿉니다)
cd ~
git clone git@github.com:<OWNER>/<REPO>.git myapp

처음 접속할 때 GitHub 서버의 지문을 신뢰할지 물으면 yes를 입력합니다. 이 부분(배포 키와 git clone)은 GitHub 문서로 확인한 절차이며 시험 환경에서는 실행하지 않았습니다. 공개 저장소라면 git clone https://github.com/<OWNER>/<REPO>.git myapp으로 바로 받을 수 있습니다.

용어 풀이

  • 배포 키(Deploy key): GitHub 저장소 하나에만 연결되는 SSH 키입니다. 기본은 읽기 전용이며, 서버가 코드를 내려받는 용도로 씁니다.

환경 변수 파일 만들기

데이터베이스 주소처럼 비밀스러운 값은 코드 저장소에 넣지 않고 서버에서 파일로 만듭니다. create-next-app으로 만든 프로젝트의 .gitignore에는 .env*가 이미 들어 있어 이런 파일이 커밋되지 않습니다. 자신의 프로젝트도 그런지 확인해 두세요.

# 서버에서 실행: 프로젝트 폴더에 운영용 환경 변수 파일 만들기
cd ~/myapp
nano .env.production

편집기에 다음처럼 적고 Ctrl+O, Enter로 저장한 뒤 Ctrl+X로 나옵니다.

DATABASE_URL=postgresql://appuser:<DB_PASSWORD>@localhost:5432/appdb
# 서버에서 실행: 다른 사용자가 읽지 못하게 권한 제한
chmod 600 .env.production

Next.js는 운영 모드에서 .env.production을 자동으로 읽습니다. 시험 환경에서도 환경 변수를 따로 넘기지 않고 이 파일만으로 API가 데이터베이스에 접속했습니다. 한 가지 주의할 점은 NEXT_PUBLIC_으로 시작하는 변수는 빌드할 때 브라우저용 코드에 값이 박혀 들어간다는 것입니다. 이런 값을 바꿨다면 서버를 재시작하는 것만으로는 반영되지 않고 다시 빌드해야 합니다. 비밀번호나 API 키에는 이 접두어를 붙이지 마세요. 브라우저에서 누구나 볼 수 있게 됩니다.

용어 풀이

  • 환경 변수: 프로그램 바깥에서 넘겨주는 설정값입니다. 같은 코드를 개발·운영 환경에서 다른 값으로 돌릴 수 있게 해 줍니다.

설치와 빌드

# 서버에서 실행: 잠금 파일 그대로 패키지 설치 후 운영용 빌드
cd ~/myapp
npm ci
npm run build

npm ci는 package-lock.json에 적힌 버전 그대로 설치합니다. 데이터베이스 표를 마이그레이션 도구로 관리한다면 빌드 전후에 그 도구의 운영용 명령을 실행합니다(Prisma라면 npx prisma migrate deploy). 빌드가 끝나면 다음처럼 경로 목록이 나옵니다. 아래는 시험 프로젝트의 실제 출력이며, /api/health는 데이터베이스에 SELECT now()를 보내는 API입니다.

Route (app)
┌ ○ /
├ ○ /_not-found
└ ƒ /api/health

○  (Static)   prerendered as static content
ƒ  (Dynamic)  server-rendered on demand

용어 풀이

  • 마이그레이션: 데이터베이스의 표 구조를 바꾸는 작업을 파일로 기록해 두고 순서대로 적용하는 방식입니다. Prisma 같은 ORM(Object-Relational Mapping, 객체-관계 매핑) 도구가 이 기능을 제공합니다.

빌드가 Killed라는 말만 남기고 멈추면 메모리가 모자란 것입니다. 이럴 때는 아래 “자주 막히는 곳”을 보세요.

7. systemd로 Next.js를 상시 실행하기

터미널에서 npm start를 실행하면 SSH 창을 닫는 순간 서비스도 꺼집니다. 서버가 켜질 때 자동으로 시작되고, 죽으면 다시 살아나도록 systemd 서비스로 등록합니다.

# 서버에서 실행: 서비스 파일 만들기
sudo nano /etc/systemd/system/myapp.service
[Unit]
Description=Next.js app (myapp)
After=network.target postgresql.service

[Service]
Type=simple
User=ubuntu
WorkingDirectory=/home/ubuntu/myapp
Environment=NODE_ENV=production
ExecStart=/usr/bin/npm start -- -H 127.0.0.1 -p 3000
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target

-H 127.0.0.1이 중요합니다. 이 옵션이 없으면 next start는 서버의 모든 네트워크 주소(*:3000)에서 연결을 받습니다. 시험 환경에서 옵션을 넣은 뒤에는 127.0.0.1:3000에서만 받는 것을 확인했습니다. Lightsail 방화벽이 3000번을 막고 있더라도, 서버 안에서 한 번 더 막아 두면 방화벽 규칙을 실수로 열었을 때도 Next.js가 직접 노출되지 않습니다.

# 서버에서 실행: 서비스 등록, 시작, 상태 확인
sudo systemctl daemon-reload
sudo systemctl enable --now myapp
systemctl status myapp
curl -s http://127.0.0.1:3000/ | head -c 200

status에 active (running)이 보이고 curl이 HTML 일부를 출력하면 됩니다. 실행 로그는 journalctl -u myapp -f로 실시간으로 볼 수 있습니다(Ctrl+C로 나옴).

8. Nginx를 앞에 세우기

이제 80번 포트로 들어온 요청을 Next.js로 넘기도록 Nginx를 설정합니다. example.com은 자신의 도메인으로 바꾸고, 도메인이 아직 없다면 그대로 두어도 IP 주소로 시험할 수 있습니다(아래에서 기본 사이트를 지우므로 이 설정이 80번 포트의 유일한 사이트가 됩니다).

# 서버에서 실행
sudo nano /etc/nginx/sites-available/myapp
server {
    listen 80;
    listen [::]:80;
    server_name example.com www.example.com;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
    }
}

proxy_set_header 줄들은 방문자의 원래 주소와 접속 방식(HTTP·HTTPS)을 Next.js에 알려 줍니다. Upgrade·Connection 두 줄은 웹소켓을 위한 것으로, 쓰지 않아도 그대로 두어 문제없습니다.

용어 풀이

  • 웹소켓: 브라우저와 서버가 연결을 끊지 않고 양쪽에서 수시로 데이터를 주고받는 통신 방식입니다. 채팅이나 실시간 알림에 씁니다.
# 서버에서 실행: 사이트 켜기, 기본 사이트 끄기, 문법 검사 후 반영
sudo ln -s /etc/nginx/sites-available/myapp /etc/nginx/sites-enabled/myapp
sudo rm /etc/nginx/sites-enabled/default
sudo nginx -t
sudo systemctl reload nginx

nginx -t가 syntax is ok와 test is successful을 출력해야 합니다. 이제 내 컴퓨터 브라우저에서 http://<고정 IP>/를 열면 서비스 첫 화면이 보입니다. 시험 환경에서는 Nginx를 거친 요청이 HTTP 200으로 응답했고, /api/health가 {"ok":true,"dbTime":"..."}처럼 데이터베이스 시각을 돌려주었습니다.

Next.js의 스트리밍(loading.tsx, Suspense로 화면을 나눠 보내는 기능)을 쓴다면 Nginx가 응답을 모아 두었다가 한꺼번에 보내지 않도록 해야 합니다. Next.js 문서는 next.config.js의 headers()에서 X-Accel-Buffering: no 헤더를 붙이는 방법을 안내합니다.

9. 도메인 연결하고 HTTPS 켜기

도메인을 고정 IP로 연결

도메인을 산 곳(가비아, 후이즈, Cloudflare 등)의 DNS 관리 화면에서 A 레코드 두 개를 만듭니다.

호스트(이름) 유형 값
@ (도메인 자체) A 고정 IP
www A 고정 IP

DNS 관리를 Lightsail로 옮기고 싶다면 Domains & DNS → Create DNS zone에서 영역을 만들고, 레코드를 추가한 뒤 도메인 등록 업체에서 네임서버를 Lightsail이 알려 주는 값으로 바꿉니다. 영역은 무료지만, 네임서버 변경은 퍼지는 데 몇 시간이 걸릴 수 있습니다. 처음이라면 도메인 업체의 DNS에 A 레코드만 추가하는 쪽이 단순합니다.

용어 풀이

  • A 레코드: 도메인 이름을 IPv4 주소 하나에 연결하는 DNS 기록입니다.
  • 네임서버: 어떤 도메인의 DNS 기록을 보관하고 응답하는 서버입니다.

레코드가 반영되었는지는 내 컴퓨터에서 nslookup example.com으로 확인할 수 있습니다. 고정 IP가 나오고 http://example.com이 열리면 다음으로 넘어갑니다.

Let’s Encrypt 인증서 발급

HTTPS 인증서는 Let’s Encrypt에서 무료로 받을 수 있고, Certbot이 발급과 Nginx 설정 수정, 자동 갱신까지 맡아 줍니다. Certbot 공식 안내는 Ubuntu에서 snap으로 설치하는 방법을 권합니다.

# 서버에서 실행 (snap 명령이 없으면 먼저 sudo apt install -y snapd)
sudo snap install --classic certbot
sudo ln -s /snap/bin/certbot /usr/local/bin/certbot
sudo certbot --nginx -d example.com -d www.example.com

처음 실행하면 연락용 이메일과 약관 동의를 묻습니다. 발급에 성공하면 Certbot이 Nginx 설정에 443번 포트와 인증서 경로를 추가합니다. 인증서는 만료 전에 자동으로 갱신되며, 갱신이 제대로 동작하는지는 다음 명령으로 미리 시험할 수 있습니다.

# 서버에서 실행: 실제로 바꾸지 않고 갱신 과정만 시험
sudo certbot renew --dry-run

용어 풀이

  • Let’s Encrypt: 웹사이트용 HTTPS 인증서를 무료로 자동 발급하는 비영리 인증 기관입니다.
  • Certbot: Let’s Encrypt 인증서를 받고 웹 서버 설정과 갱신을 자동으로 처리해 주는 프로그램입니다.
  • snap: Ubuntu에서 쓰는 패키지 형식 가운데 하나로, 프로그램을 필요한 파일과 함께 묶어 배포하고 자동으로 업데이트합니다.
  • TLS(Transport Layer Security) 인증서: 이 서버가 도메인의 진짜 주인임을 증명하고 암호화 통신에 쓰는 전자 문서입니다.

발급이 실패하는 가장 흔한 이유는 세 가지입니다. 도메인이 아직 고정 IP를 가리키지 않거나, Lightsail 방화벽에 80번이 막혀 있거나(Let’s Encrypt가 80번으로 소유권을 확인합니다), Nginx 설정의 server_name이 -d로 넣은 도메인과 다를 때입니다. 이 단계는 실제 도메인이 필요해서 시험 환경에서는 실행하지 못했고, Certbot 공식 안내로 확인한 절차입니다.

코드를 고친 뒤 다시 배포하기

로컬에서 코드를 고쳐 GitHub에 푸시했다면 서버에서는 같은 순서를 반복하면 됩니다. 매번 치기 번거로우니 스크립트로 만들어 둡니다.

# 서버에서 실행: 재배포 스크립트 만들기
cat > ~/deploy.sh <<'EOF'
#!/bin/bash
set -euo pipefail
cd ~/myapp
git pull --ff-only
npm ci
npm run build
sudo systemctl restart myapp
EOF
chmod +x ~/deploy.sh

# 이후 재배포할 때마다
~/deploy.sh

set -euo pipefail 때문에 중간 단계가 하나라도 실패하면 스크립트가 그 자리에서 멈추고, 빌드가 실패한 코드로 서버가 재시작되지는 않습니다. 다만 이 방식은 실행 중인 서버가 쓰는 .next 폴더를 빌드가 덮어쓰므로, 빌드와 재시작 사이의 수십 초 동안 일부 요청이 실패하거나 잠깐 접속이 끊길 수 있습니다. 방문자가 적은 서비스라면 감수할 만하지만, 끊김이 없어야 한다면 빌드를 다른 폴더에서 한 뒤 바꿔 끼우는 방식이나 GitHub Actions에서 빌드한 결과물을 올리는 방식으로 발전시켜야 합니다.

용어 풀이

  • GitHub Actions: GitHub 저장소에 코드를 올릴 때마다 빌드·검사·배포 같은 작업을 자동으로 실행해 주는 GitHub의 기능입니다.

백업: 스냅샷과 pg_dump를 함께

서버 한 대에 데이터베이스까지 넣었으니 백업은 직접 챙겨야 합니다. 두 가지를 함께 쓰는 것을 권합니다.

자동 스냅샷은 인스턴스 관리 화면의 Snapshots 탭에서 Automatic snapshots 스위치를 켜면 됩니다. 매일 한 번 디스크 전체를 저장하고 최근 7개를 보관하며, 저장 용량에 따라 GB당 월 $0.05가 붙습니다. 서버가 망가졌을 때 통째로 되살리기 좋습니다. 단, 자동 스냅샷은 원본 인스턴스를 지우면 함께 지워집니다. 오래 남길 것은 수동 스냅샷으로 복사해 두세요.

pg_dump는 데이터베이스만 따로 떠 두는 방법입니다. PostgreSQL 문서에 따르면 pg_dump는 실행을 시작한 순간의 일관된 상태를 저장하고, 그동안 다른 읽기·쓰기를 막지 않습니다. 디스크 전체 스냅샷보다 작고, 다른 서버나 관리형 DB로 옮길 때도 그대로 쓸 수 있습니다.

# 서버에서 실행: 날짜를 붙인 덤프 파일 만들기
mkdir -p ~/backups
sudo -u postgres pg_dump -Fc appdb > ~/backups/appdb-$(date +%F).dump

# 복원할 때 (기존 데이터 위에 덮어쓰므로 먼저 현재 상태를 덤프해 두세요)
sudo -u postgres pg_restore -d appdb --clean ~/backups/appdb-2026-11-12.dump

같은 서버 안의 덤프는 서버가 통째로 사라지면 함께 사라집니다. 중요한 데이터라면 덤프 파일을 주기적으로 내 컴퓨터(scp)나 다른 저장소로 옮겨 두세요. 덤프 파일에는 데이터가 그대로 들어 있으니 공개된 곳에 두면 안 됩니다.

자주 막히는 곳

증상 흔한 원인 확인·해결
브라우저에서 502 Bad Gateway Next.js가 꺼져 있거나 시작에 실패 systemctl status myapp, journalctl -u myapp -n 50으로 오류 확인
빌드가 Killed로 멈춤 메모리 부족 다른 서비스를 잠시 멈추고 다시 빌드하거나, 스냅샷으로 더 큰 플랜의 인스턴스를 만들어 옮기기
http://는 되는데 https://가 안 열림 방화벽에 443번이 없음, 또는 IPv6 방화벽에만 빠짐 Networking 탭에서 IPv4·IPv6 양쪽에 HTTPS 규칙 확인
서버를 재시작했더니 접속이 안 됨 고정 IP를 붙이지 않아 공인 IP가 바뀜 2단계대로 고정 IP를 붙이고 DNS의 A 레코드 수정
앱 로그에 password authentication failed .env.production의 비밀번호 오타, 또는 특수문자가 URL에서 깨짐 16진수 비밀번호로 다시 만들고 ALTER ROLE appuser PASSWORD '...'로 변경
바꾼 NEXT_PUBLIC_ 값이 반영 안 됨 이 값은 빌드할 때 고정됨 npm run build 후 sudo systemctl restart myapp
git pull이 Permission denied (publickey) 배포 키가 등록되지 않았거나 ~/.ssh/config가 빠짐 ssh -T git@github.com으로 인증 확인

관리형 데이터베이스로 바꾸고 싶다면

데이터베이스 관리(업데이트, 백업, 장애 대응)를 직접 하기 부담스럽다면 Lightsail의 관리형 데이터베이스로 PostgreSQL만 분리할 수 있습니다. 2026년 11월 12일 기준 PostgreSQL 12~16을 고를 수 있고, 가장 작은 표준 플랜이 월 $15(메모리 1GB, SSD 40GB)입니다. 다른 가용 영역에 예비 서버를 두는 고가용성 플랜은 두 배 가격입니다. 시점 복원 백업이 기본으로 켜져 있어, 이 글의 pg_dump 같은 작업을 직접 하지 않아도 됩니다.

용어 풀이

  • 고가용성: 서버 한 대가 멈춰도 예비 서버가 이어받아 서비스가 계속 돌아가게 하는 구성입니다.
  • 시점 복원: 백업 보관 기간 안의 원하는 시각으로 데이터베이스를 되돌려 새 데이터베이스로 만드는 기능입니다.

바꿀 때는 관리형 DB를 같은 리전에 만든 뒤 pg_dump로 옮기고, .env.production의 DATABASE_URL을 관리형 DB의 주소로 바꿔 재시작하면 됩니다. 대신 한 달 요금이 $12에서 $27로 늘어납니다. 서비스 초기에는 이 글처럼 한 서버에 두고, 데이터가 중요해지거나 서버 메모리가 모자라기 시작할 때 분리하는 순서가 비용 면에서 무난합니다.

정리하며 남겨 둘 것

  • 연습용으로 만든 인스턴스는 중지가 아니라 삭제해야 요금이 멈춥니다. 삭제는 되돌릴 수 없으니 필요한 데이터는 수동 스냅샷이나 pg_dump로 먼저 받아 두고, 남은 고정 IP와 수동 스냅샷도 함께 정리하세요.
  • AWS Budgets에서 월 예산 알림을 걸어 두면 데이터 전송량 초과처럼 예상하지 못한 요금을 일찍 알아챌 수 있습니다.
  • 서버 보안 업데이트는 자동으로 다 되지 않습니다. 한 달에 한 번쯤 sudo apt update && sudo apt upgrade를 실행하고, 그 전에 스냅샷을 하나 떠 두면 문제가 생겨도 되돌릴 수 있습니다.

기준과 한계

  • 요금과 플랜, 블루프린트 목록, 관리형 DB의 PostgreSQL 버전은 2026-11-12에 Lightsail 요금 페이지와 공식 문서에서 확인했습니다. 금액은 세금 별도 미국 달러입니다.
  • 서버 안의 명령(패키지 설치, PostgreSQL 설정, 빌드, Nginx 프록시, 재배포, pg_dump)은 Windows 11의 Docker 컨테이너(ubuntu:24.04, Ubuntu 24.04.5 LTS, 메모리 2GB·CPU 2개 제한)에서 실행해 확인했습니다. 실제 Lightsail 인스턴스의 Ubuntu 이미지와는 기본 설치 프로그램이 다를 수 있습니다.
  • Lightsail 콘솔 조작, 고정 IP·방화벽·스냅샷 설정, 배포 키 등록, 도메인 연결, Certbot 인증서 발급은 각 공식 문서로만 확인했고 직접 실행하지 않았습니다. 콘솔 메뉴 이름과 배치는 바뀔 수 있습니다.
  • systemd 서비스 파일은 systemd-analyze verify로 문법만 검사했고, 컨테이너에서는 같은 명령(npm start -- -H 127.0.0.1 -p 3000)을 직접 실행해 동작을 확인했습니다.
  • 빌드 시간과 메모리 수치는 새로 만든 시작 프로젝트에서 한 번 잰 값이며, 실제 프로젝트의 규모와 Lightsail 인스턴스의 CPU 성능에 따라 달라집니다.
