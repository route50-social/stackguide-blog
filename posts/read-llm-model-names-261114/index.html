Local LLM

모델 이름 읽는 법: 파라미터(7B), 컨텍스트, 양자화(Q4)

'Meta-Llama-3.1-8B-Instruct-Q4_K_M' 같은 모델 이름을 조각내어 파라미터 수, 미세 조정 목적, 컨텍스트 길이, 양자화 방식을 읽는 법을 정리하고, 이름만 보고 필요한 메모리를 어림하는 계산까지 실제 파일 값으로 확인합니다.

로컬에서 LLM을 돌려 보려고 모델 저장소를 열면 Meta-Llama-3.1-8B-Instruct-Q4_K_M.gguf 같은 파일이 수십 개 늘어서 있습니다. 이름 끝의 몇 글자만 다를 뿐인데 크기는 3GB에서 32GB까지 벌어집니다. 어느 것을 받아야 내 컴퓨터에서 돌아가는지, 8B나 Q4_K_M이 무슨 뜻인지 모르면 고르기가 막막합니다.

용어 풀이

  • LLM(Large Language Model, 대규모 언어 모델): 아주 많은 글을 학습해 문장을 이어 쓰는 큰 규모의 언어 모델입니다. 이 글에서는 내려받아 내 컴퓨터에서 실행하는 공개 모델을 주로 다룹니다.
  • 로컬 LLM: 클라우드 서비스가 아니라 내 PC나 서버에서 직접 실행하는 LLM입니다. 모델 파일 전체를 내려받아 메모리에 올려야 합니다.

다행히 이런 이름에는 규칙이 있습니다. 이 글에서는 위 파일 이름을 조각내 읽고, 조각마다 실제 파일에서 어떤 값으로 확인되는지 살펴본 다음, 이름만 보고 필요한 메모리를 어림하는 방법까지 계산해 보겠습니다. 예시는 Meta의 Llama 3.1 8B를 llama.cpp용 GGUF 형식으로 변환한 파일입니다.

용어 풀이

  • GGUF: llama.cpp 개발자가 만든 모델 파일 형식입니다. 모델의 숫자 데이터와 함께 이름·크기·컨텍스트 길이 같은 정보(메타데이터)를 한 파일에 담아, 내려받은 파일 하나만으로 모델을 실행할 수 있게 합니다.
  • llama.cpp: LLM을 CPU나 일반 그래픽카드에서도 돌릴 수 있게 만든 C/C++ 오픈 소스 실행 도구입니다. Ollama, LM Studio 같은 도구도 이 계열의 기술을 바탕으로 GGUF 파일을 실행합니다.

이름을 조각으로 나누면

GGUF 형식 문서에는 파일 이름을 짓는 규칙이 따로 있습니다. 기본 이름, 크기, 미세 조정 목적, 버전, 인코딩(양자화 방식) 순서로 조각을 놓고 하이픈(-)으로 잇습니다. 문서는 이 규칙의 목적을 “사람이 한눈에 모델의 가장 중요한 정보를 알아보기 쉽게 하는 것”이라고 설명하면서, 실제로 쓰이는 이름이 워낙 다양해 완벽하게 해석되지는 않는다고 덧붙입니다. 규칙은 길잡이일 뿐 모든 저장소가 그대로 지키지는 않는다는 뜻입니다.

그림 1. 모델 파일 이름의 구성 요소와 Ollama 태그의 대응 (자료: ggml GGUF Naming Convention 문서, Ollama llama3.1 태그 페이지, 2026-11-14 확인)

그림의 예시 파일에서 버전 조각은 따로 없고, 대신 기본 이름 Meta-Llama-3.1 안에 세대 번호가 들어가 있습니다. 이 파일의 GGUF 메타데이터를 직접 읽어 보면 general.basename = Meta-Llama-3.1, general.size_label = 8B, general.finetune = Instruct로 저장되어 있어, 파일 이름이 메타데이터에서 그대로 만들어졌다는 것을 확인할 수 있습니다(2026-11-14, Hugging Face에서 파일 앞부분 2MB를 내려받아 Node.js 24.22.2로 머리말을 읽은 결과).

Ollama는 같은 정보를 다른 모양으로 적습니다. 콜론 앞이 모델 이름이고, 뒤의 태그에 크기·목적·양자화가 들어갑니다. 2026-11-14에 Ollama 태그 페이지를 확인해 보니 llama3.1:latest, llama3.1:8b, llama3.1:8b-instruct-q4_K_M 세 태그가 같은 식별자(46e0c10c039e)와 같은 크기(4.9GB)로 표시되었습니다. 그냥 ollama pull llama3.1이라고 하면 8B 대화용 모델의 Q4_K_M 판을 받는 셈입니다.

용어 풀이

  • Ollama(올라마): 내 컴퓨터에서 LLM을 내려받아 실행하고, 다른 프로그램이 HTTP API로 쓸 수 있게 해 주는 오픈 소스 도구입니다. 모델:태그 형식으로 모델을 고릅니다.
  • Hugging Face(허깅페이스): 공개 AI 모델과 데이터셋을 올리고 내려받는 저장소 서비스입니다. 원본 모델과 여러 사람이 변환한 GGUF 파일이 함께 올라옵니다.

이제 조각을 하나씩 보겠습니다.

8B: 모델 안에 든 숫자의 개수

8B의 B는 Billion, 즉 10억입니다. 8B는 파라미터가 약 80억 개라는 뜻입니다. GGUF 명명 규칙은 이 자리에 쓰는 단위로 K(천), M(백만), B(10억), T(조), Q(천조)를 정해 두었습니다. 그래서 작은 모델에는 135M, 1.5B처럼 소수점이나 M이 붙기도 합니다.

용어 풀이

  • 파라미터(Parameter, 매개변수): 학습 과정에서 조정되는 모델 내부의 숫자입니다. 모델이 데이터에서 배운 내용은 이 숫자들에 담기고, 개수가 많을수록 파일과 필요한 메모리도 커집니다.

이름의 숫자는 반올림한 값입니다. Hugging Face가 이 파일에서 읽어 보여 주는 정확한 파라미터 수는 8,030,261,312개이고, Ollama 모델 페이지에도 8.03B로 표시됩니다. 같은 저장소에 있는 32비트 원본 파일(f32)의 크기는 32,128,885,888바이트인데, 파라미터 80억 3천만 개에 숫자 하나당 4바이트를 곱한 값과 거의 같습니다. 파일 크기는 결국 “파라미터 수 × 숫자 하나의 크기”로 정해진다는 점을 기억해 두면 뒤의 양자화가 쉽게 이해됩니다.

이 값은 Hugging Face API로 직접 확인할 수 있습니다. 아래 명령은 Windows 11 Pro의 Git Bash에서 curl 8.9.0과 Node.js 24.22.2로 실행했고, 출력은 2026-11-14에 실제로 받은 결과입니다.

# 실행 위치: 로컬 PC (Windows 11 Pro, Git Bash, curl 8.9.0, Node.js 24.22.2)
# 전제: 인터넷 연결. 로그인이나 토큰은 필요 없는 공개 저장소입니다.
curl -s "https://huggingface.co/api/models/bartowski/Meta-Llama-3.1-8B-Instruct-GGUF?expand[]=gguf" \
  | node -e "let s='';process.stdin.on('data',d=>s+=d).on('end',()=>{const g=JSON.parse(s).gguf;console.log(JSON.stringify({total:g.total,architecture:g.architecture,context_length:g.context_length}))})"
{"total":8030261312,"architecture":"llama","context_length":131072}

8x7B와 30B-A3B: 전문가가 나뉜 모델

크기 자리에 8x7B나 30B-A3B처럼 기호가 섞인 이름도 있습니다. 이런 모델은 MoE 구조입니다. 모델 안에 여러 개의 전문가 묶음을 두고, 토큰마다 그중 일부만 골라 계산합니다.

용어 풀이

  • MoE(Mixture of Experts, 전문가 혼합): 모델의 일부를 여러 개의 “전문가” 묶음으로 나눠 두고, 입력마다 몇 개만 골라 계산하는 구조입니다. 전체 파라미터는 많지만 한 번에 계산에 쓰는 파라미터는 적습니다.
  • 토큰(Token): 언어 모델이 글을 처리하는 기본 단위입니다. 단어 하나일 수도, 단어의 일부나 글자 하나일 수도 있습니다.

GGUF 규칙에서 8x7B는 “전문가 8개 × 7B”를 뜻합니다. 그렇다고 8 곱하기 7로 56B가 되지는 않습니다. Mistral AI는 Mixtral 8x7B를 소개하면서 전체 파라미터는 46.7B이고 토큰 하나를 처리할 때는 12.9B만 쓴다고 밝혔습니다. 전문가로 나뉜 것은 모델의 일부(피드포워드 블록)이고 나머지는 함께 쓰기 때문입니다.

Qwen3의 30B-A3B는 표기 방식이 다릅니다. 앞의 30B가 전체 크기, A3B가 한 번에 활성화되는(Activated) 크기입니다. 모델 카드에는 전체 30.5B, 활성 3.3B, 전문가 128개 가운데 8개를 활성화한다고 적혀 있습니다.

로컬 실행에서 이 구분이 중요한 이유가 있습니다. 활성 파라미터가 적으면 토큰 하나를 만드는 계산이 가벼워져 속도에 유리하지만, 어떤 전문가가 뽑힐지 미리 알 수 없으니 파일 전체는 메모리에 올라가 있어야 합니다. llama.cpp 양자화 문서도 “모델은 현재 메모리에 전부 올라간다”고 설명합니다. 그래서 30B-A3B는 3B 모델처럼 빠르게 움직일 수 있어도, 필요한 메모리는 30B 모델 기준으로 어림해야 합니다.

Instruct: 대화용으로 다듬었는지

크기 뒤의 Instruct는 미세 조정의 목적입니다. GGUF 규칙은 이 자리에 Chat, Instruct 같은 이름을 예로 듭니다. Llama 3.1 모델 카드는 같은 크기의 모델을 사전 학습만 마친 판과 지시를 따르도록 다듬은 판(instruction tuned)으로 나눠 공개하고, 다듬은 판은 다국어 대화용, 사전 학습 판은 다른 용도로 고쳐 쓰기 위한 바탕이라고 설명합니다.

용어 풀이

  • 베이스 모델(Base Model): 사전 학습만 마친 모델입니다. 질문에 답하기보다 주어진 글을 자연스럽게 이어 쓰는 데 가깝습니다.
  • 인스트럭션 튜닝(Instruction Tuning): 질문과 모범 답변 쌍으로 추가 학습해 사람의 지시를 따르고 대화하도록 다듬는 과정입니다.

이 자리가 비어 있는 이름은 보통 베이스 모델입니다. Ollama에서는 대화용이 -instruct, 베이스 모델이 -text 태그로 나뉘어 있습니다(예: llama3.1:8b-text-q4_K_M). 채팅 상대로 쓰려고 받았는데 엉뚱하게 문장만 이어 쓴다면, 이 조각부터 확인해 보는 것이 좋습니다.

컨텍스트: 이름에 없어도 꼭 봐야 하는 값

예시 파일 이름에는 컨텍스트 길이가 들어 있지 않습니다. 일부 모델은 -128k처럼 이름 끝에 붙이기도 하지만, 대부분은 모델 카드나 파일 메타데이터에서 확인해야 합니다.

용어 풀이

  • 컨텍스트 윈도우(Context Window): 모델이 한 번에 볼 수 있는 토큰 수의 한도입니다. 입력한 글과 모델이 쓴 답, 이전 대화 내용을 합한 길이가 이 안에 들어가야 합니다.

Llama 3.1 모델 카드는 8B, 70B, 405B 모두 128k 컨텍스트를 지원한다고 적고 있고, 앞의 API 출력에서도 context_length가 131,072로 나왔습니다. 128k의 k는 여기서 1,024를 뜻해 128 × 1,024 = 131,072토큰입니다.

그런데 모델이 128k를 지원한다고 해서 실행 도구가 늘 그만큼 쓰는 것은 아닙니다. Ollama 문서(2026-11-14 확인)는 기본 컨텍스트 길이를 그래픽카드 메모리에 따라 정한다고 설명합니다. 24GiB 미만이면 4k, 24~48GiB면 32k, 48GiB 이상이면 256k입니다. 일반적인 PC라면 128k 모델을 받아도 4k로 돌아가고, 긴 문서를 넣으면 앞부분이 잘려 나갈 수 있다는 뜻입니다. 늘리려면 서버를 OLLAMA_CONTEXT_LENGTH 환경 변수와 함께 실행하거나 API 요청에 num_ctx를 넣고, ollama ps의 CONTEXT 열로 실제 값을 확인합니다. 이 부분은 이번에 Ollama를 직접 실행해 보지 못했고 공식 문서로만 확인한 내용입니다.

용어 풀이

  • VRAM(Video RAM, 그래픽 메모리): 그래픽카드에 달린 메모리입니다. 모델이 VRAM에 전부 올라가면 빠르게 돌고, 넘치면 일부가 PC의 일반 메모리로 밀려나 느려집니다.

컨텍스트를 늘리면 메모리가 더 듭니다

기본값이 작게 잡혀 있는 데는 이유가 있습니다. 모델은 지금까지 읽은 토큰의 계산 결과를 KV 캐시라는 곳에 쌓아 두고 다음 토큰을 만들 때 다시 씁니다. 컨텍스트가 길수록 이 캐시가 커집니다.

용어 풀이

  • KV 캐시(Key-Value Cache): 모델이 이미 읽은 토큰마다 계산해 둔 중간값(키와 값)을 저장해 두는 메모리 공간입니다. 다시 계산하지 않아도 되니 빨라지지만, 컨텍스트 길이에 비례해 메모리를 차지합니다.

크기는 모델 구조 값으로 계산할 수 있습니다. 예시 파일의 메타데이터에는 층(block_count) 32개, 키·값 헤드(head_count_kv) 8개, 임베딩 크기 4,096과 어텐션 헤드 32개(헤드 하나당 128차원)가 적혀 있습니다. 키와 값 두 가지를 16비트(2바이트)로 저장한다고 하면 토큰 하나에 2 × 32 × 8 × 128 × 2 = 131,072바이트, 곧 128KiB가 듭니다.

컨텍스트 길이 KV 캐시(f16 기준 계산값)
4,096토큰 (Ollama 기본값, VRAM 24GiB 미만) 512MiB
32,768토큰 4GiB
131,072토큰 (모델 최대) 16GiB

표 1. Llama 3.1 8B의 컨텍스트 길이별 KV 캐시 크기. GGUF 메타데이터의 구조 값으로 계산한 이론값이며, 실제 사용량은 실행 도구의 구현과 설정에 따라 달라집니다.

모델 파일은 5GB가 안 되는데 컨텍스트를 최대로 열면 캐시만 16GiB가 됩니다. Ollama FAQ에 따르면 이 캐시도 양자화할 수 있어서, Flash Attention을 켠 상태에서 OLLAMA_KV_CACHE_TYPE을 q8_0으로 두면 기본값 f16의 약 절반, q4_0이면 약 4분의 1로 줄어듭니다. 대신 정밀도가 조금씩 떨어집니다. 여러 요청을 동시에 처리하도록 설정하면 그 수만큼 컨텍스트 크기가 늘어난다는 점도 FAQ에 적혀 있습니다.

Q4_K_M: 숫자를 몇 비트로 줄였는지

마지막 조각이 양자화 방식입니다. 원래 파라미터는 16비트나 32비트 실수로 저장되는데, 이를 더 적은 비트의 정수와 보정값으로 바꿔 파일과 메모리를 줄이는 것이 양자화입니다.

용어 풀이

  • 양자화(Quantization): 모델 파라미터를 더 적은 비트의 숫자로 바꿔 저장하는 방법입니다. 파일 크기와 메모리 사용량이 줄어드는 대신 정확도가 조금 떨어질 수 있습니다.
  • 비트(bit)와 bpw(bits per weight): 비트는 0 또는 1 하나를 담는 정보의 최소 단위입니다. bpw는 파라미터 하나를 저장하는 데 평균 몇 비트를 쓰는지 나타내는 값입니다.

Q4_K_M은 세 부분으로 읽습니다.

  • Q4: 4비트 양자화(Quantized)입니다. 숫자가 작을수록 더 많이 줄인 것입니다. Q2부터 Q8까지 있고, 양자화하지 않은 판은 F16, BF16, F32처럼 실수 형식 이름을 씁니다.
  • K: llama.cpp의 k-quant 방식입니다. 파라미터 256개를 하나의 큰 묶음(슈퍼 블록)으로 잡고, 그 안을 작은 블록으로 나눠 블록마다 배율과 최솟값을 따로 저장합니다. Hugging Face의 GGUF 문서는 이 보정값 때문에 Q4_K가 4비트가 아니라 파라미터당 4.5비트가 된다고 설명합니다. K가 없는 Q4_0, Q8_0은 더 단순한 예전 방식이고, IQ4_XS처럼 I로 시작하는 이름은 중요도 행렬을 참고해 숫자를 고르는 또 다른 방식입니다.
  • M: 섞는 정도입니다. 모든 부분을 같은 비트로 줄이지 않고, 결과에 영향이 큰 일부를 더 높은 정밀도로 남깁니다. k-quant를 처음 도입한 llama.cpp PR의 설명에 따르면 Q4_K_S는 모든 텐서를 Q4_K로 저장하고, Q4_K_M은 attention.wv와 feed_forward.w2 텐서의 절반을 Q6_K로, 나머지를 Q4_K로 저장합니다. S(Small), M(Medium), L(Large) 순으로 커집니다.

용어 풀이

  • 텐서(Tensor): 모델 파라미터를 담는 여러 차원의 숫자 배열입니다. 모델 파일은 역할이 다른 수백 개의 텐서로 이루어져 있습니다.

그래서 Q4_K_M의 실제 평균은 4비트보다 꽤 높습니다. llama.cpp 양자화 문서가 Llama 3.1 8B로 측정한 표에서 Q4_K_M은 파라미터당 4.8944비트, 파일 크기 4.58GiB입니다. Hugging Face에 올라온 예시 파일의 크기는 4,920,739,232바이트로, GiB로 바꾸면 4.58GiB가 되어 문서 값과 맞습니다.

그림 2. 양자화 방식별 Llama 3.1 8B 파일 크기와 파라미터당 비트 수 (자료: llama.cpp tools/quantize README의 meta-llama/Llama-3.1-8B 측정표, 2026-11-14 확인)

용어 풀이

  • GiB와 GB: GiB(기비바이트)는 2의 30제곱(1,073,741,824)바이트, GB(기가바이트)는 10의 9제곱(1,000,000,000)바이트입니다. 같은 파일이 4.58GiB로도, 4.9GB로도 표시되는 것은 단위가 달라서입니다.

어느 단계를 고를지는 메모리와 품질 사이의 선택입니다. 비트를 줄일수록 원래 모델과 결과가 달라질 여지가 커지는데, 얼마나 달라지는지는 모델과 작업마다 다르고 이번에 직접 측정하지는 않았습니다. 다만 Ollama가 llama3.1의 기본 태그를 Q4_K_M으로 정해 둔 것처럼, 4비트 K 계열은 크기와 품질의 균형점으로 널리 쓰입니다. 메모리에 여유가 있으면 Q5_K_M이나 Q6_K, Q8_0으로 올려 보고, 빠듯하면 같은 비트 안에서 S를 고르거나 한 단계 낮추는 식으로 접근하면 됩니다. 같은 메모리라면 큰 모델을 많이 줄인 것과 작은 모델을 덜 줄인 것 중 무엇이 나은지도 작업마다 다르니, 직접 써 보며 비교하는 편이 확실합니다.

이름만 보고 메모리 어림하기

지금까지의 조각을 합치면 이름만으로 필요한 메모리를 대략 계산할 수 있습니다.

모델 파일 크기(GB) ≈ 파라미터 수(B) × 파라미터당 비트 수 ÷ 8
필요한 메모리     ≈ 모델 파일 크기 + KV 캐시(컨텍스트 길이에 비례) + 실행 도구의 작업 공간

예시 파일로 확인해 보면 8.03 × 4.8944 ÷ 8 ≈ 4.91GB(4.58GiB)로 실제 파일 크기와 맞습니다. 여기에 Ollama 기본 컨텍스트 4k의 KV 캐시 0.5GiB를 더하면 약 5.1GiB이고, 실행 도구가 쓰는 계산용 공간이 조금 더 붙습니다. 8GB VRAM 그래픽카드라면 4k 컨텍스트에서는 여유가 있지만, 컨텍스트를 32k로 늘리면 캐시만 4GiB가 되어 넘칠 수 있다는 판단이 섭니다. 넘치면 Ollama는 모델 일부를 일반 메모리로 옮겨 실행하고, ollama ps의 PROCESSOR 열에 48%/52% CPU/GPU처럼 나뉜 비율이 표시됩니다(Ollama FAQ 기준).

같은 계산으로 70B Q4_K_M은 70 × 4.89 ÷ 8 ≈ 43GB가 나오고, llama.cpp 문서의 Llama 3.1 70B Q4_K_M 크기 43.1GB, Ollama의 llama3.1:70b 43GB와 맞습니다. 정확한 비트 수를 모르면 Q4 계열은 4.5~5비트, Q8_0은 8.5비트 정도로 잡으면 크게 틀리지 않습니다.

이름이 알려 주지 않는 것

이름은 크기와 형식을 알려 줄 뿐, 모델의 실력이나 이용 조건은 알려 주지 않습니다. 같은 8B라도 세대와 학습 데이터에 따라 성능이 크게 다르고, 한국어를 얼마나 잘하는지도 이름에는 드러나지 않습니다. 라이선스도 모델마다 다릅니다. Llama 3.1은 Llama 3.1 Community License를 따르고, 다른 모델은 Apache 2.0 등 각자의 조건을 붙입니다.

또 Hugging Face의 GGUF 파일은 원 개발사가 아니라 다른 사람이 변환해 올린 경우가 많습니다. 이 글의 예시 파일도 Meta가 아닌 개인 저장소(bartowski)의 변환본입니다. 파일을 받을 때는 원본 모델이 무엇인지, 변환에 쓴 도구 버전과 설정이 적혀 있는지 저장소 설명을 함께 확인하고, 상업적으로 쓸 계획이라면 원본 모델의 라이선스를 직접 읽어 보는 것이 안전합니다.

정리하면 Meta-Llama-3.1-8B-Instruct-Q4_K_M은 “Meta Llama 3.1 계열, 파라미터 약 80억 개, 대화용으로 다듬은 판, 평균 4.9비트로 줄인 파일”이라고 읽습니다. 이름에 없는 컨텍스트 길이는 모델 카드나 메타데이터에서 확인하고, 실행 도구가 실제로 몇 토큰을 쓰는지 따로 살펴보면 됩니다.
